# Lean and ELPI types

This paper explains how data types, functions and variables declared on one side of LeanElpi become usable on the other side, what we took from Coq-Elpi, and where Lean forced a different answer.

It extends [[papers/type-bridge]], which fixes the principle (plain ELPI types for programs, Lean types checked by Lean), with the machinery that makes the principle pleasant to use. The decision is [[decisions#Two-way type bridge]], the requirements are in the OpenSpec capability `lean-interop`, and the code is [[components#Type interoperability]].

## What Coq-Elpi teaches

Coq-Elpi has had ten years to find out what an embedded λProlog needs from its host; four of its answers carry over directly and one does not.

**Declarations are data.** In Coq-Elpi an inductive type is an ordinary Elpi value (`indt-decl`) that a program can read with `coq.env.indt` and build for `coq.env.add-indt`. This is what makes the `derive` family of tools writable in Elpi: they read one inductive and add its `map`, `eq` and `param1` companions. LeanElpi had `lean.add_decl` for definitions only, so a Lean program could be generated by ELPI but a Lean *type* could not. Closing that gap is [[papers/interop#Declarations as data]].

**One vocabulary per side, generated from one declaration.** Coq-Elpi keeps its own data types in Elpi and does not duplicate them in Coq: what crosses the boundary is the term language, plus a handful of typed carriers (`gref`, `int`, `string`, `indt-decl`). Users who want their own Coq-side data convert by hand. LeanElpi makes the conversion mechanical instead: [[papers/interop#Lean to ELPI types]] and [[papers/interop#ELPI to Lean types]] derive each side from a single declaration.

**Typed predicates for host functions.** Coq-Elpi's `coq.*` API is a set of predicates with *declared types and modes*, implemented in OCaml and checked by the Elpi type checker at load time. LeanElpi already had the registry for such builtins (tier T2 of [[papers/solvers]]) but its implementations were untyped, `Array Term → LazyList (Array Term)`. [[papers/interop#Lean functions as predicates]] derives the typed signature from the Lean function type.

**Quotations in both directions.** `{{ … }}` and `lp:` exist in LeanElpi since M3 ([[papers/type-bridge#Quotations]]) and need nothing new.

**What does not carry over** is the idea that the host's term language is the shared data type. Coq-Elpi can put all of CIC into one HOAS type because Coq's terms *are* the data users care about. In Lean ordinary programs are full of *non-term* data (a `Shape`, an `Env`, a `Tree α`), and Lean has no `Elpi Db` module system to hold ELPI-side types. The environment extension that `deriving Elpi` writes to plays that role.

| Coq-Elpi | LeanElpi |
|---|---|
| `{{ … }}`, `lp:` | `{{ … }}`, `lp:{{ }}` (M3) |
| `coq.env.indt` | `lean.env.indt` |
| `coq.env.add-indt` | `lean.add_inductive` |
| typed `coq.*` predicates in OCaml | `elpi_extern` on a Lean function |
| Elpi data types, hand-converted | `deriving Elpi` and `elpi_data`, both directions |
| `Elpi Db` for shared declarations | the derived-signature environment extension |

## The shared vocabulary

A type crosses the boundary exactly when ELPI's simple types can express it: an inductive type or structure with `Type` parameters, no indices, and fields that themselves cross.

That is the *plain data* fragment. It is deliberately the same fragment that keeps unification decidable ([[constraints#CIC unification is undecidable]]). Everything else has a home elsewhere: indexed families and dependent fields go through `Expr` reflection or the LF extension ([[papers/certified-lf]]), proofs stay on the Lean side, and functions cross through [[papers/interop#Lean functions as predicates]] rather than as values.

The correspondence is by name and shape.

| Lean | ELPI |
|---|---|
| `inductive Tree (α : Type)` | `kind tree type -> type.` |
| constructor `node (l : Tree α) (a : α) (r : Tree α)` | `type node tree A -> A -> tree A -> tree A.` |
| `structure Point` | `kind point type.` and `type point.mk int -> int -> point.` |
| `Nat`, `Int`, `String`, `Bool`, `Float` | `int`, `int`, `string`, `bool`, `float` |
| `List α`, `Option α`, `α × β` | `list A`, `option A`, `pair A B` |
| `Lean.Expr`, `Name`, `Level` | `term`, `name`, `level` |

## Lean to ELPI types

`deriving Elpi` turns a Lean type into ELPI declarations and the two conversion instances; parameters become prenex type variables and recursion is free.

```lean
inductive Tree (α : Type) where
  | leaf
  | node (l : Tree α) (a : α) (r : Tree α)
  deriving Elpi

#elpi_signature Tree
-- kind tree type -> type.
-- type leaf tree A.
-- type node tree A -> A -> tree A -> tree A.
```

The generated instances are `[ToElpi α] → ToElpi (Tree α)` and `[FromElpi α] → FromElpi (Tree α)`. Before this change the handler rejected every parametric type and, in fact, every recursive one, because the instance being defined was not yet available inside its own definition. The generated `partial def` now binds the instance for the type under definition as a *local* instance, so a recursive field (`Tree α`) and a nested one (`List (Rose α)`) are both found by ordinary instance search.

Type variables are named by position: the first parameter is `A`, the second `B`. The Lean names are not preserved, because ELPI type variables must start with a capital letter and Lean parameters are usually Greek.

An indexed family such as `Vec α n` is still rejected, with an error that names the LF extension. The same goes for a parameter that is not a `Type`.

## ELPI to Lean types

`elpi_data` goes the other way: write the type where the logic lives, get the Lean inductive for free.

```lean
elpi_data lp%{
  kind shape type.
  type circle int -> shape.
  type square int -> shape.
  type beside shape -> shape -> shape.
}%
```

defines `inductive Shape | circle : Int → Shape | square : Int → Shape | beside : Shape → Shape → Shape deriving Elpi`, which then registers exactly the declarations above. Because the second step is the ordinary `deriving Elpi`, there is one code path for the ELPI text of a type and a round trip is a tested property, not a hope.

A program written against `shape` can be queried from Lean and the answer decoded at the Lean type:

```lean
#eval show MetaM _ from do
  let m ← Elpi.query areas "mirror (beside (circle 1) (square 2)) M"
  return m.head?.bind (fun | .ok sol => (sol.get? "M" : Option Shape) | _ => none)
-- some (Shape.beside (Shape.square 2) (Shape.circle 1))
```

A kind with the single constructor `<kind>.mk` becomes a Lean `structure`, with fields named `f0`, `f1`, … because ELPI constructors carry no field names. A constructor argument of function type, as in `type lam (tm -> tm) -> tm`, is refused: a Lean inductive cannot have that negative occurrence, and binders belong to [[glossary#HOAS]] terms (`term`) or to LF. Nothing is defined when any error occurs.

## Lean functions as predicates

`elpi_extern f` exposes a Lean function as an ELPI predicate whose signature is computed from the function's type.

```lean
def twice (n : Nat) : Nat := 2 * n
elpi_extern twice                      -- pred twice i:int, o:int.

def half (n : Nat) : Option Nat := …
elpi_extern partial half               -- fails on none

def divisors (n : Nat) : List Nat := …
elpi_extern many divisors as "divisor" -- one solution per element
```

The three forms are the three determinism classes of a logic predicate: a total function has exactly one solution, a partial function has at most one, a multi-valued function has many. Arguments are decoded with `FromElpi` and the result is encoded with `ToElpi`, so every type from the vocabulary above is allowed, derived types and instantiated parameters included (`tr-size : Tr Nat → Nat`). ELPI's own type checker checks calls against the computed signature when the program is loaded, so `twice "x" X` is rejected before it runs; an argument that nevertheless fails to decode makes the predicate fail.

Underneath, a class `ElpiFn F R` peels the arguments of a function type one at a time and the helpers `Extern.total`, `Extern.partial_` and `Extern.many` turn the result into a lazy list of solutions. The wrapper is registered as an ordinary tier-T2 builtin, so it persists in the `.olean`, is visible in importing modules and is undone on backtracking by the same rules as every builtin ([[papers/solvers#Tier 2: Lean builtins]]).

## Declarations as data

`lean.env.indt` reads a complete inductive type into ELPI and `lean.add_inductive` adds one, so ELPI programs can generate types and not only definitions.

```elpi
kind lean.ctor type.   type lean.ctor  name -> term -> lean.ctor.
kind lean.indt type.   type lean.indt  name -> int -> int -> term -> list lean.ctor -> lean.indt.

pred lean.env.indt     i:name, o:lean.indt.
pred lean.add_inductive i:lean.indt.     % commands only
```

An `lean.indt` carries the name, the number of parameters and indices, the type and the constructors, each with its reflected type. `lean.add_inductive` calls the kernel and then builds the same auxiliary constructions the `inductive` command builds (`casesOn`, `recOn`, `noConfusion`, `below`, `brecOn`), so the new type can be matched on and used in structural recursion. The test copies `Option` to `MyOption` with a short ELPI command and then defines a function on it by pattern matching.

The builtin is restricted to commands, like `lean.add_decl` ([[glossary#Phase restriction]]); a tactic that calls it fails with the phase error and the environment is unchanged. The kernel remains the trust anchor ([[constraints#Kernel is the trust anchor]]): a malformed inductive is rejected by it, whatever ELPI believed.

## Variables

The word "variable" means three different things across the boundary, and each has its own bridge.

| Variable | Lean side | ELPI side | Bridge |
|---|---|---|---|
| type parameter | `α` in `Tree α` | prenex type variable `A` in `type node tree A -> …` | `deriving Elpi`, `elpi_data` |
| local hypothesis or `variable` | free variable `fvar` in a local context | eigenvariable under `pi x\`, assumed with `=>` | tactic goals, [[papers/type-bridge#Plain Types and Independent Types#Reflecting Lean terms as HOAS#Hypotheses and eigenvariables]] |
| unknown | metavariable `?m` | unification variable `X` | reification turns each ELPI variable into a Lean metavariable; `lean.mk_mvar` goes the other way |

Type parameters are the new entry: they are fixed at declaration time and only ever instantiated, never unified, which is why prenex polymorphism is enough. Hypotheses and unknowns were already covered by M3 and need no change.

## What does not cross

The bridge is explicit about its limits, because a silent approximation would be worse than an error.

- **Indexed families and dependent fields** are rejected, with a pointer to LF.
- **Proofs and `Prop` fields** are not data; use `lean.defeq` and tactics.
- **Functions as values** are not data either; they cross as predicates through `elpi_extern`, or as `term`s.
- **Higher-order constructors** are refused by `elpi_data`; use `term` for binders.
- **Type classes** do not cross yet. Instance resolution in Lean and clause resolution in ELPI are both tabled Prolog-like searches, and a bridge in either direction is the obvious next step, recorded as an open question of the change.

## As built

All pieces are in `Elpi/Lean/Marshal.lean` (the deriving handler), `Elpi/Lean/Interop.lean` (`elpi_data`, `elpi_extern`, `#elpi_signature`) and `Elpi/Lean/Builtins.lean` (`lean.env.indt`, `lean.add_inductive`), with tests under `tests/Interop/`.

Registered builtin signatures may now mention derived kinds and types: the program assembler loads derived declarations before registered signatures, and the registry checks a signature against them. This is what lets `elpi_extern` accept `Tr Nat` as an argument.
